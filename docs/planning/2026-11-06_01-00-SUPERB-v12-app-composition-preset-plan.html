Pareto Plan · SUPERB v12

Kill the re-assembly tax

The 39 Go apps adopt the atomic building blocks everywhere (branded-id 34×, error-family 34×, httputil 24×) — and hand-assemble them ~20–30 times. go-appkit, the composition layer, is the least-adopted core module: 6/39 direct. This plan makes composition the default: one preset, one config battery, one scaffold, then an adoption wave.

Pareto thesis. One percent of the work — a single preset.New() composing batteries that already shipped — removes 51% of the per-app integration burden, because every future app AND every migration lands on it. Config first (the preset's env binding), scaffold next (kills new-app copy-paste), then the per-repo swap wave.

01Findings

The paradox

Adoption counts (direct go.mod requires, all 39 apps): branded-id 34, error-family 34, etag 25, go-sse 24, httputil 24, codec 23, cqrs-lite 22, flightrecorder 22, templ-components 21 … go-appkit 6. The repo whose mission is "make it easy for my apps to smartly use all my libs together" is the least-used member of the very stack it composes. The blocks are consumed; the assembly is rewritten per app.

Presets get adopted; parts catalogs don't

The one composition product with real adoption is cqrs-htmx setup.New() — 10 apps, one call, dispatcher + auth + SSE + errorpages + service. dnsblockd re-implements appkit/otel (777 LOC), appkit/systemd (59), appkit/security (~590); ChastityAPI re-implements ~4,800 LOC of the same battery set; PapDashboard hosts appkit and still hand-rolls the security battery 1:1. The batteries exist — the cheap path to them does not.

Root cause

Opt-in-everything + no swap recipes + no scaffold

audit §4 — docs/review/apps/2026-11-06_integration-burden-audit.md

Each battery is a separate module and a separate wiring decision; most apps predate the batteries; nothing makes adopting cheaper than keeping the hand-roll; every new app starts by copy-pasting a cousin's config/logger/CLI/flake.
