Pareto Plan · SUPERB v12 · rev 2

Kill the re-assembly tax

39 Go apps adopt the atomic blocks everywhere — and hand-assemble the same ten-lib stack ~20–30 times. go-appkit, the composition layer, is the least-adopted core-family module: 6/39 direct, 8/39 counting transitive rides, below every block it exists to compose. This plan makes composition the default: one config battery, one preset, one scaffold — then an adoption wave onto them.

Pareto thesis. One percent of the work — a single preset.New() composing batteries that already shipped — removes 51% of the per-app integration burden, because every future app AND every migration lands on it. Config first (the preset's env binding), scaffold next (kills new-app copy-paste), then the per-repo swap wave.
Number hygiene. Adoption figures appear as any / direct pairs throughout this plan. The audit's original table mislabeled any-require counts as direct (same-day errata, strict recount); every number below uses the verified dual-column recount. Conclusion unchanged under both definitions — the gap widens under the strict one.

The healthy poles — what "good" looks like today

quotaboard (main.go:80–135): cqrs-htmx MustNew + appkit.NewService + systemd.Install + StartHooks/ShutdownHooks refresher — and still hand-writes slog setup, config.FromEnv, dispatcher recovery, route mounting. media-atlas: cmdguard ×15 verbs + appkit + testkit + errorpages — each subsystem a hand-written register* glue function. The pattern is consistent: where a preset exists (setup), adoption follows; where assembly is manual, everyone assembles.

05Root causes

Cause 1

Timing + no swap recipes

audit §4

Most apps predate the batteries (core v0.9.0, security v0.2.0, systemd v0.1.0, otel v0.3.0 — all Aug–Oct 2026). Nothing makes adopting cheaper than keeping the hand-roll.

Cause 2

No appkit-side preset

§01 read-out 4

The one composition product that works covers only event-sourced HTMX apps. Non-cqrs apps — and even setup apps for config/logger glue — assemble by hand.

Cause 3

Opt-in-everything posture

PapDashboard exemplar

Each battery is a separate module + separate wiring decision. Hosting appkit ≠ composed batteries. Env-driven defaults are absent.

Cause 4

No scaffold

ledger rows 9–12

Every new app copy-pastes a cousin's config/logger/CLI/flake/buildflow (37/39 flakes). The fleet has website templates and an unbuilt wizard SDK — no service scaffold.
