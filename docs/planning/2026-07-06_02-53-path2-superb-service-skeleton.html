01Why appkit Exists

The question that must be answered first

If httputil already has Server + Health + 13 middlewares, why does appkit exist at all? Why not put logger+sqlite+signal into httputil?

Answer: httputil is HTTP-only by enforcement, not just convention

httputil's depguard linter restricts imports to $gostd + github.com/larsartmann/go-error-family. Adding database/sql, modernc.org/sqlite, log/slog init, and os/signal would violate httputil's design contract. These are different concerns at a different layer:

Layer map ├─ Domain layer go-cqrs-lite (events, commands, aggregates) ├─ App framework cqrs-htmx (HTMX, Casbin, templ, CQRS dispatch) ├─ HTTP utilities httputil (Server, middleware, health, CORS, compression) ├─ Service skeleton appkit (logger init, SQLite open, signal, shutdown orchestration) └─ Go stdlib net/http, log/slog, database/sql, os/signal

appkit is the composition layer that wires httputil's HTTP primitives together with logger init, database bootstrap, and signal-based lifecycle. It sits above httputil and below the application. httputil cannot absorb it without breaking its own scope contract.

03Design Decisions (the hard choices)

These are decisions that shape the entire API. They must be made before coding, not discovered during.

Decision 1

Does Service own the mux?

Affects: NewService, Service.Mux accessor, consumer ergonomics

Yes. Service creates and owns the *http.ServeMux, exposed via svc.Mux. Consumers register routes on it. Rationale: if the consumer creates the mux, they must also wire health registration and middleware themselves — defeating the purpose. The mux is the composition point.

Alternative considered: Consumer passes mux to NewService(cfg, mux). Rejected: forces consumer to know about health registration ordering and middleware wrapping.

Decision 2

Does Run(ctx) block?

Affects: Service.Run, signal handling, consumer main() shape

Yes, it blocks. Run(ctx) starts the server, waits for signal or ctx.Done(), shuts down, then returns. This is the main() terminator — the last line. Rationale: the entire value proposition is "one method and you're running." A non-blocking Run would force the consumer to write the signal-wait loop themselves.

For advanced use: Start(ctx) <-chan error remains available for consumers who need non-blocking behavior (tests, embedded servers).

Decision 3

Is the middleware stack replaceable or extendable?

Affects: ServiceConfig.ExtraMiddlewares vs ServiceConfig.Middlewares

Extendable only. The default stack (Recovery → RequestID → Logging → Timeout → SecurityHeaders) always runs. Consumers add via cfg.ExtraMiddlewares []httputil.Middleware. Rationale: Recovery and Logging are safety-critical. Letting consumers remove them by accident is a footgun. If a consumer truly needs a different stack, they use httputil directly.

Decision 4

Is SQLite the only database?

Affects: ServiceConfig.SQLitePath, future Postgres support

Yes, for v1. SQLite is the only DB bootstrap. Postgres is a non-goal for v1.0.0. Rationale: SQLite is the 80% case for Go services (embedded, single-file, WAL). Adding Postgres means connection pooling, schema migration strategy, and a driver dependency — all scope creep. Consumers who need Postgres use database/sql directly; appkit doesn't block that.

Decision 5

Version target?

Affects: API stability, go.mod, tag strategy

v1.0.0. The Service API is the v1 contract. After that, additive-only until v2. Tag v1.0.0 when tests pass and README is honest.

06Before / After (real code, real APIs)

Before (today — ~40 lines of wiring)
After (Path 2 — ~12 lines)
// Today: consumer wires everything manually
func main() {
    logger, _ := appkit.InitLogger(appkit.LoggerConfig{})
    db, _ := appkit.OpenSQLite(ctx, appkit.SQLiteConfig{
        Path: "app.db",
    })
    mux := http.NewServeMux()
    // no recovery, no request-id, no logging middleware
    // no security headers, no timeout
    srv := appkit.NewServer(appkit.DefaultServerConfig(), mux)
    go func() { _ = srv.Start(ctx) }()
    appkit.WaitForSignal(ctx, cfg, func(sctx context.Context) error {
        _ = srv.Shutdown(sctx)
        _ = db.Close()
        return nil
    })
}
// Path 2: appkit does it all
func main() {
    svc, err := appkit.NewService(appkit.ServiceConfig{
        Addr:       ":8080",
        SQLitePath: "app.db",
        LogLevel:   appkit.LogLevelInfo,
    })
    if err != nil { log.Fatal(err) }
    defer svc.Close()

    // recovery, request-id, logging, timeout,
    // security headers already wired
    svc.Mux.HandleFunc("GET /", handler)

    // blocks until signal, then graceful shutdown
    if err := svc.Run(ctx); err != nil {
        log.Fatal(err)
    }
}

13Graceful Degradation

Scenario 1

DB unreachable at startup

NewService → OpenSQLite fails

Hard fail. NewService returns the error. Service never starts. This is correct: if the database is required and unavailable, starting the server would serve a broken service. The error is classified as Infrastructure via go-error-family.

Scenario 2

DB drops at runtime

Server running, DB connection lost

Ready-probe fails. The consumer wires httputil.ReadyHandlerWithProbe(func() bool { return db.Ping() == nil }). Kubernetes stops sending traffic. The server stays up (liveness passes) but ready fails. Consumer decides whether to also trigger shutdown.

Scenario 3

No DB configured

ServiceConfig.SQLitePath == ""

Service starts without DB. svc.DB is nil. Health endpoints return 200 (no dependency to check). This is valid for stateless services or services using external DB clients.

15Risks & Tradeoffs

Risk 1

httputil.Server.Addr() returns string, not net.Addr

server.go delegation — task 6

httputil's Addr() returns the configured address string, not the live listener address. appkit's current Addr() returns net.Addr from the listener — critical for tests using :0 (random port).

Mitigation: appkit owns the net.Listener directly (does NOT delegate listener management to httputil). Service.Addr() returns s.ln.Addr(). httputil.Server is used only for its http.Server wrapper + Shutdown.
Risk 2

cqrs-htmx (the main consumer of httputil) only uses httputil.ClientIP. The Server type has no battle-tested integration. appkit will be its first real consumer.

Mitigation: If httputil.Server proves problematic, appkit can fall back to owning http.Server directly while still using httputil's middleware + health. The middleware is the higher-value composition; Server is a thin wrapper.
