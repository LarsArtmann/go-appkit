PARETO EXECUTION PLAN · 2026-11-21

SUPERB v17: make go-appkit the default, not just the standard

The 28-review adoption corpus shows go-appkit winning every evaluation it is qualified for while 11 of 27 fleet projects decline on fit, doctrine, or timing. The reputation is "the fleet's server standard"; the goal is "the default every project builds on." This plan routes the 1% / 4% / 20% that close that gap.

Evidence: 28-review corpus + TODO_LIST Step-0 pass Baseline: direct 7/41 (fixed counter) · 7 of 27 reviewed Owner gates: 2 (ruling, repo create)

00Why appkit is not the default yet

Four structural causes, none of them quality. (1) Timing: the fleet's services pre-built appkit from the same primitives — retrofit never pays, so the only funnel is greenfield, and greenfield moments have been rare since v0.10–0.12 made appkit credible. (2) Unit of adoption: "appkit's unit of adoption is the service, not a component" (nextd) — one-capability consumers must take the core. (3) Opinion collisions: charmbracelet/log v1 vs the fleet's v2 lane, forced samber/do, TCP-only bind — appkit reads as a different opinion, not the default shape. (4) No on-ramp: seven decliners wrote "next service starts from appkit" into private reviews; no template, no start-here page, no scaffold mechanizes that moment. The levers below attack 4 first (cheapest), then 3, then ride 1 and 2 as trains.

The one-sentence strategy Encode the default by policy, mechanize the first hour, ship the three named seams — everything else is trains and docs that ride them.
