Tests pass only because they bypass the appkit stack. Root cause is pinned to request re-forking in httputil middlewares; fix is small but lives in a sibling repo. 04d) TOTALLY FUCKED UP — found today

Silent production regression

Span names collapse to the bare method; http.route metrics are lost through the documented wiring

otel/middleware.go (bridge) · httputil RequestID/Timeout/Logging (forks) · otelhttp v0.71 handler.go:187

Through OuterMiddlewares — the exact wiring the README and package doc prescribe — every SERVER span flushes as GET/POST instead of GET /users/{id}, and the http.route metric attribute disappears entirely. Live-verified today: the example service flushed Name: "GET". Consequences: per-route latency dashboards and span-name aggregation are impossible; the module's two headline claims (pattern-named spans, cardinality safety) are dead in production wiring — silently, with all 23 tests green, because the tests wrap the mux directly and skip the appkit stack.

Root cause (pinned by A/B bisection): otelhttp names/attributes from r.Pattern read back on its OWN request fork (r = r.WithContext(ctx); next.ServeHTTP(w, r); if r.Pattern != ""). ServeMux assigns the pattern to the request pointer IT receives; any middleware between otel and the mux that forks again (RequestID, Timeout, Logging's ctx helper — all r.WithContext) leaves otel's fork with Pattern == "". otel adjacent to the mux: works. Otel outermost with one fork in between: broken. Deterministic in the real Service, in a hand-built server, and in the live example — version-independent, so NOT caused by the v0.68→v0.71 bump. It has been broken since the feature shipped.

Fix In httputil, forking middlewares retain the fork and propagate the pattern up: r2 := r.WithContext(ctx); next.ServeHTTP(w, r2); r.Pattern = r2.Pattern (3 sites: requestid.go:82, timeout.go:18, context.go:31). Then pin a regression test in the integration module asserting span name + http.route through the full default stack, and re-tag.
Until then Document the limitation in the otel README (known-issues note) — do not let the cardinality-safety claim sell a dead feature. Full bisection recorded in TODO_LIST P2 (2026-09-15 entry).

07g) TOP #1 QUESTION

Which fix path for the pattern loss — httputil contract change, or in-repo reimplementation?

Option A (recommended, small): patch httputil's three forking middlewares to copy r2.Pattern back onto the request they received after next.ServeHTTP returns. Three one-liners, ecosystem-wide benefit — but it mutates a shared *http.Request post-handler, which is a public contract decision in a repo you own separately, and it triggers a release train (httputil patch → otel re-tag → integration test). Option B (in-repo only): go-appkit/otel stops relying on otelhttp's pattern readback and resolves route + span name itself — no cross-repo dependency, but it re-implements otelhttp internals and must track upstream semconv changes forever. A decides the next session's shape: which way?
