00Summary

go-appkit is not a casual consumer of go-flightrecorder — it is the library’s adapter layer. Three modules exist to put the recorder in front of traffic: flightrecorder (HTTP middleware + manual snapshot endpoint), flightrecorderhealth (health-dashboard visibility + auto-capture on failing health batches), and the cqrs projection wiring, plus an OTel metrics bridge in otel. That surface is adopted with real discipline: the process-global singleton constraint is designed around rather than fought, the ops sink stack (directory + retention + compression) is composed as a preset, the health path captures asynchronously exactly as the library’s README prescribes, and all five pinning modules sit on the latest tag. The gaps are precise, not diffuse: the HTTP middleware — the hottest path in the family — still uses the blocking SnapshotIf, the one place the library’s own docs say not to; the observability hooks are invited everywhere and registered nowhere, leaving retention-cleanup failures invisible; and the debug endpoint reports that a trace was captured instead of handing the trace over, though the library ships SnapshotToWriter for exactly that endpoint.

The bottom line Verdict: strong adoption (73/100) with a short, high-leverage punch list. The score is dragged down almost entirely by one architectural choice — synchronous capture on the request goroutine — and two unwired seams (the library’s logger hook and the repo’s own OTel bridge). Nothing is a misuse; every fix is additive and local, and together they take this to ~90.

◆What's already excellent

Before the findings: six things this codebase already does superbly. Each one is the pattern other consumers of this library should copy.

+
One-recorder discipline is designed in, not bolted on The process-global singleton is the sharpest edge in the library, and every module respects it: the cqrs config explicitly offers one shared recorder for HTTP + projection captures (cqrs/eventservice.go:92-104), the health adapter treats nil as pass-through (adapter.go:181-183), and the middleware re-arms the once-latch instead of spawning recorders (middleware.go:110-112).
+
The ops sink stack is composed exactly as the library intends OpsRecorderPreset returns the production posture in one spread-friendly call: directory sink + multi-instance prefix + retention + size cap + gzip-3 + 10s MinAge — 6 of the library’s 10 options (preset.go:31-40), documented as “a CONVENIENCE PRESET, not magic” so consumers append their own hooks.
+
Async capture on the health path matches the guidance to the letter SnapshotIfAsync(context.WithoutCancel(ctx), …) (adapter.go:213) is the exact pattern the fr README prescribes for hot paths: detached context, non-blocking, mutex held only for nanoseconds around the decision.
+
TriggerContext fidelity at every integration point Kind/Type/Duration/Err are populated everywhere: “http” + “METHOD /path” + threshold-classified error (middleware.go:88-93), “health.check”/“batch” + first failing service (adapter.go:189-194), “projection”/name/terminal error (cqrs). This is the contract SnapshotEvent’s dashboard labels were built for.
+
Cooldown exists because the library lacks it WithCooldown is a correct mutex-guarded rate limit (adapter.go:205-219; the lock spans read + write so two concurrent batches cannot both decide the cooldown elapsed) that protects directory sinks from flapping-service trace floods. The library should absorb this — see the appendix.
+
Version currency: 5/5 modules pin the latest tag v0.2.0 (2026-08-11) is the newest release; the 17 commits since are an internal captureOnce dedup, a CI bump, and docs — zero public API in the gap (verified by git diff v0.2.0..HEAD). The integration module’s documentedPins fixture + check-pin-drift.sh keep the pins honest.

01Findings

These are the issues that need attention, ordered by impact.

Missed opportunity · High impact

The HTTP middleware captures traces synchronously — on the exact hot path the library says not to

flightrecorder/middleware.go:95 · 7 sync call paths in flightrecorder_test.go

go-flightrecorder’s README (lines 154-156) is unambiguous: SnapshotIfAsync “captures in a background goroutine so trace I/O never blocks the hot path (e.g., HTTP middleware)”. The canonical HTTP adapter — the one the library’s own ROADMAP names as an official integration — calls the blocking SnapshotIf instead. With the default WithAutoReset(true), every trigger-matching request re-arms the latch and blocks again: a latency incident that trips fr.OnLatency(50ms) makes every slow request additionally pay the trace write — a buffer the library docs size at ~10 MB of trace data per busy second, up to 64 MiB under the ops preset, gzip-3 — i.e. tens to hundreds of milliseconds added to exactly the requests already having a bad day. Blocking is correct on the manual debug endpoint; it is the wrong default per-request. 

// Before (middleware.go:95) — blocking write on the request goroutine:
captured := rec.SnapshotIf(r.Context(), tc, trigger)

// After — capture leaves the request path; context outlives the write:
captured := rec.SnapshotIfAsync(context.WithoutCancel(r.Context()), tc, trigger)
Fix: switch to SnapshotIfAsync and log from the hook The health adapter already demonstrates the exact pattern (adapter.go:213). Move the “trace snapshot captured” log line into a fr.WithMetrics hook keyed on event.Source/event.Kind — the method and path are already carried in TriggerContext.Type. Tests should assert capture completion via the hook rather than the HTTP response.
Missed opportunity · Medium impact

The /debug endpoint reports that a trace was captured — instead of delivering the trace

flightrecorder/handler.go:41-48 · SnapshotToWriter call sites: 0

SnapshotToWriter’s own godoc names this endpoint as its reason to exist: “the low-level escape hatch for callers that need a one-shot capture to an arbitrary destination (e.g., an HTTP response buffer for a /debug/trace endpoint)”. SnapshotHandler instead writes to the configured sink and returns a JSON status line — so the operator must shell into the box to fetch the artifact, and in writer-sink setups (every in-memory/test configuration in this repo) the captured bytes are not inspectable at all. The library built the escape hatch; the adapter never uses it. 

// In SnapshotHandler, before the sink write:
if r.URL.Query().Has("download") {
    w.Header().Set("Content-Type", "application/octet-stream")
    w.Header().Set("Content-Disposition", `attachment; filename="trace.trace.gz"`)
    _, _ = rec.SnapshotToWriter(r.Context(), w) // respects compression
    return
}
Fix: an opt-in download mode Keep the sink behavior as the default; add ?download=1 streaming the buffer straight into the response. Turns the endpoint from “trust me, it’s captured” into “here is the artifact”.
Partially used · High impact

fr.WithLogger is registered nowhere — so retention-cleanup failures are invisible

0 registrations repo-wide · preset.go:31-40 (invites appending it) · two parallel hand-rolled loggers: middleware.go:36-38, adapter.go:119-121

The ops preset composes six options and its godoc explicitly invites appending fr.WithMetrics/fr.WithLogger — nobody ever does. The consequence is silent: with WithMaxSnapshots retention, “cleanup failures are reported via WithLogger and never fail a snapshot” (WithMaxSnapshots godoc). With no hook registered, a failing cleanup — disk full, permissions — produces no error anywhere while the trace directory fills. Start/stop lifecycle diagnostics are lost the same way. Meanwhile two hand-rolled logging options exist in the adapters that cover capture events only; the library hook is the only one that sees what the wrappers cannot. 

rec, err := fr.New(append(appkitfr.OpsRecorderPreset(dir, 5, 64<<20),
    fr.WithLogger(func(format string, args ...any) {
        slog.Warnf(format, args...) // retention-cleanup failures land here
    }))...)
Fix: make the logger a first-class part of the ops story Either an OpsRecorderLoggerPreset(dir, maxSnapshots, maxBytes, log) variant, or — lighter — a compile-checked example that appends fr.WithLogger to the preset, which is exactly the extension point the preset documents.
Partially used · Medium impact

The OTel metrics bridge: built, tested — and wired to nothing

otel/frmetrics.go:29 · frmetrics_e2e_test.go:26-45 · shipped call sites: 0

NewFlightRecorderMetricsHook translates fr.SnapshotEvent into appkit_flightrecorder_snapshots_total{source,kind} plus a duration histogram, with an E2E test that runs a real capture cycle against a real meter provider — and then nothing in the repository calls it outside its own tests. It appears in no example, no README, no preset. The hook also drops SnapshotEvent.Type (frmetrics.go:52-55 labels source and kind only), although the library carries the field precisely “so dashboards can label by operation (e.g. http.request vs event.handler)” (observe.go doc). 

attrs := metric.WithAttributes(
    attribute.String("source", event.Source),
    attribute.String("kind", event.Kind),
    attribute.String("type", event.Type), // add
)
Fix: ship the seam, not just the bridge Wire fr.WithMetrics(appkitotel.NewFlightRecorderMetricsHook(meter)) into the otel example main, add the type attribute, and document the metric names in the otel README’s signal table — the module already treats metric names as a published contract (frmetrics.go:11-16).
Partially used · Low impact

Composite triggers OnAny / OnAll: zero call sites, zero documentation

repo-wide: 4 of 6 triggers in use · OnAny/OnAll unused

OnError, OnAlways, OnErrorOrLatency, and OnLatency are all in active use across the adapters and cqrs defaults. The composites are not — including in docs. OnAll is the documented cure for capture noise under error storms (“fire only on slow errors, not fast errors”) which is directly relevant once findings 1 and 3 land: async capture + directory sink + a broad error trigger can churn trace files at retention speed during a storm. 

// Fire only on SLOW errors — fast failures stay log-only:
trigger := fr.OnAll(fr.OnError(), fr.OnLatency(500*time.Millisecond))
Fix: guidance where consumers look Add the narrowing pattern to the module’s doc.go cookbook and use it in the ops example (finding 7).
Partially used · Low impact

Typed errors are never handled — a double-start yields a raw AlreadyEnabledError

0 references to ErrAlreadyEnabled / ConfigError / SnapshotError repo-wide · shared-recorder posture documented at cqrs/eventservice.go:92-104

The library’s error taxonomy — ErrAlreadyEnabled, *ConfigError, *SnapshotError with errors.Is/As support — is leaned on nowhere in shipped code or examples. The exposed edge is startup: the documented posture is ONE shared recorder serving HTTP and projections, so a consumer who starts a second recorder (their own boot code plus a library example) gets a raw *AlreadyEnabledError from Start() with no error-family classification and no pointer to the sharing pattern. 

if err := recorder.Start(); err != nil {
    if errors.Is(err, fr.ErrAlreadyEnabled) {
        // one recorder per process: reuse the active one, don't start a second
    }
}
Fix: classify at the wiring boundary Map the sentinel to errorfamily.Infrastructure in start-hook wrappers and show the errors.Is check in the ops example.
Process gap · Medium impact

No runnable ops example — the production loop exists only as doc snippets

flightrecorder/ has no example/ directory · doc.go:10-30 snippets · repo standard: “doc snippets are code”

The module’s own repo standard (go-appkit AGENTS.md Gotchas) is: “Doc snippets are code: compile-check README/doc.go examples in a scratch module before shipping.” The full production loop — OpsRecorderPreset + Start + Middleware + SnapshotHandler + WithMetrics/WithLogger + Close on shutdown hooks — is assembled nowhere. The sibling otel and health modules each ship a live-verified example main; this adapter predates that convention, and it is the module where option-combination mistakes (missing logger, missing Start, dir sink without retention) are easiest to make. 

// example/main.go — the full loop, compile-checked like its siblings:
rec, _ := fr.New(append(appkitfr.OpsRecorderPreset(dir, 5, 64<<20), hooks...)...)
rec.Start()        // wired via appkit StartHooks; errors.Is(ErrAlreadyEnabled) guarded
defer rec.Close()  // drains in-flight async captures on shutdown
appkitfr.Middleware(rec, fr.OnErrorOrLatency(100*time.Millisecond))
appkitfr.Mount(svc.Mux, "POST /debug/flightrecorder/snapshot", rec)
Fix: one example binds findings 1-6 together An example/main.go in the module (PORT-env override per house style) makes every recommendation above demonstrable and keeps the doc-snippet contract enforceable.

Reverse finding: what the library is missing (upstream candidate)

The health adapter hand-rolls a cooldown because the library offers no rate limiting: a mutex-guarded lastCapture check (adapter.go:96-135, 205-219) with the lock deliberately spanning decision + dispatch. The HTTP middleware will want the same protection once capture goes async against a directory sink (finding 1). A WithMinInterval(d)-style recorder option would delete the adapter code and protect every consumer — a candidate upstream ask, to be verified against the fr repo’s TODO_LIST before filing.
