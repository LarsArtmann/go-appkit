00Summary

go-appkit’s cqrs module adopted system.New early (v0.5.0, 2026-09-07) and gets the two-config split, the operator precedence chain, lifecycle, DLQ, flight-recorder, and metrics wiring genuinely right — and the 2026-10-06 dependency sweep left every go-cqrs-lite pin at the latest published tag. But the wrapper constructs system.DomainConfig internally and never exposes it: consumers cannot declare a single metaengine read model. Every Lookup, QuerySet, Count, or Evolve fold — the entire “Store + Query declarations” half of ADR-0123 that the library’s own guidance calls required for new code — is unreachable except through hand-rolled raw projectionhost projections. Two smaller findings compound it: ~150 lines of hand-rolled checkpoint plumbing that duplicates system’s engine-backed default (ADR-0142), and a hand-rolled in-flight drain that bypasses the Drainer seam and skips GracefulClose entirely on drain timeout.

The bottom line Verdict: not yet “superb”. The wrapper commands the C in CQRS superbly and the metaengine barely at all. One API addition — an EventConfig.Domain passthrough mirroring the existing EventConfig.Deployment passthrough — unlocks the read-model planner, typed Find/Get reads, the coeffect typo gate, command-lifecycle auditing, and engine-backed timers in one move.
Re-run 2026-10-07 The bottom line above aged one day: EventConfig.Domain shipped in cqrs/v0.7.0 (2026-10-06) and the 2026-10-07 hardening follow-ups pinned its behavior end-to-end. Re-scored adoption: 87/100 — see Rubric re-run. Residuals are upstream-bounded (Timers stop gap, GracefulClose drain-error early return) and tracked under doc/feedback/outgoing/.

◆What’s already excellent

Baseline from the consumer side: cqrs/eventservice.go and cqrs/commands.go (all citations against system v4.10.2 / metaengine v4.16.1, the exact pinned versions).

+
The two-config split is honored exactly as designed Operators get the full precedence chain Deployment > ConfigPath (koanf YAML + CQRS_ env) > Driver/DSN/Pragmas (cqrs/eventservice.go:205-263), and a full *system.DeploymentConfig passthrough field. The consumer never touches infrastructure — precisely the D11 contract.
+
Version currency is perfect system v4.10.2, metaengine v4.16.1, sqliteengine v4.5.1, projectionadapter v4.5.2 — every pin IS the latest published tag (2026-10-06 sweep). Zero features missed by being behind.
+
The bootstrap-Count host guarantee is clever and documented A zero-cost counter over a never-emitted event type keeps the projection host alive for raw host projections (cqrs/eventservice.go:445-482) — and system’s memory-engine fallback means the host is never nil.
+
Lifecycle & ops wiring is first-rate Derived-wiring-wins HostOptions ordering, fail-closed DLQ store requirement for non-sqlite drivers, one shared *fr.Recorder type across HTTP and projection captures, a backend-agnostic MetricsRecorder plus an OTel implementation, and read-your-writes staleness guards that match the library’s intended read-time-check posture (cqrs/commands.go:86-104).
+
Correct layering of metaengine as an indirect dependency The wrapper does not hand-wire engines; it blank-imports sqliteengine for driver registration and lets system own planning — the right shape per ADR-0123. The gap is the sealed declaration surface, not the layering.

Missed Opportunity · High impact Resolved at cqrs/v0.7.0

The wrapper seals DomainConfig — the entire metaengine read-model surface is unreachable

cqrs/eventservice.go:473-485 (buildSystem hard-codes DomainConfig) · cqrs/eventservice.go:51-143 (EventConfig has no Domain seam) · README.md:28 teaches raw es.Host().Register(myProjection)

What the library offers: system.DomainConfig.Projections accepts sealed declarations from the Count / Evolve / Lookup[R] / QuerySet[R] builders (filterable/sortable fields become engine indexes), Evolutions share folds across projections, and typed reads come free via system.Find[R], system.Get[R], system.GetCount. The planner auto-projects them across interchangeable engines — this is the “Store + Query[Q,R]” pattern the library’s own adoption guidance marks REQUIRED for new code (ADR-0123).

What the project does instead: buildSystem constructs the DomainConfig internally with a single bootstrap counter, and EventConfig exposes no way to add to it — declarations are only readable at system.New time (system constructor.go:56-59, 137-186). Consumers are steered to hand-rolled raw projectionhost projections: manual event decoding, manual state, manual reads — exactly the low-level wiring the composition root exists to eliminate. Also sealed behind the same wall: the Events coeffect gate (catches a typo’d event subscription at startup instead of as a silently-never-updating projection), ProjectionTypeDecoder (the recommended decoder), WithCommandLifecycle (one-call command audit trail, ADR-0117), DomainConfig.Timers + sys.TimerEngine() (engine-backed scheduled commands, ADR-0142), and ShutdownDependencies.

Impact: every go-appkit CQRS consumer pays a per-read-model tax of hand-written projection + read code that the planner generates, with no index pushdown, no typed reads, and no typo gate. This is the single largest lever in the audit.

Recommendation Mirror the existing Deployment passthrough with a Domain passthrough (or discrete fields), merged so derived wiring still wins conflicts. System already auto-wires a projection adapter into the existing host, so declarations flow through unchanged infrastructure. 
// EventConfig gains the developer seam:
type EventConfig struct {
    // ... existing fields ...
    // Domain carries developer declarations: Projections
    // (system.Lookup/QuerySet/Count/Evolve), Evolutions, decoders,
    // Events coeffect gate, Timers, ShutdownDependencies.
    Domain *system.DomainConfig
}

// Consumer declares read models instead of hand-rolling projections:
es, _ := cqrs.NewEventService(cqrs.EventConfig{
    DSN: "app.db",
    Domain: &system.DomainConfig{
        Projections: []system.ProjectionDeclaration{
            system.QuerySet[TaskView]("tasks").
                On("task.created", TaskCreated{}).
                Filterable("status", "priority").
                Sortable("priority", true).Done(),
        },
    },
})

// Typed, index-backed reads for free:
tasks, _ := system.Find[TaskView](ctx, es.System(), "tasks",
    system.Where("status", "active"), system.Limit(10))
Partially Used · Medium-high impact Resolved at cqrs/v0.7.0

~150 lines of hand-rolled checkpoint plumbing vs system’s engine-backed default (ADR-0142)

cqrs/eventservice.go:286-443 (openAuxResources, buildAuxStores, applyCheckpointSchema, auxDSN, deploymentUsesSQLiteFile)

What the library offers: when DomainConfig.CheckpointStore is nil, system persists checkpoints as a system_checkpoints Map collection on the deployment-declared engine — durable wherever the engine is, no extra connection (DomainConfig godoc, ADR-0142, in the pinned v4.10.2; constructor.go resolveCheckpointStore). The sqlite engine implements the Map backend, so the wrapper’s default sqlite deployments get durable checkpoints by doing nothing.

What the project does instead: for every sqlite-file deployment it opens a second *sql.DB, applies the checkpoint schema by hand, and builds eventstore.NewSQLiteCheckpointStore — overriding the better default with duplicated infrastructure. Note the aux handle remains justified for the DLQ default (projectionhost.NewSQLiteDeadLetterStore needs a *sql.DB; system offers no engine-backed DLQ) — only the checkpoint half is removable.

Bonus doc drift: EventConfig.CheckpointStore’s comment and the README row claim non-sqlite drivers get “in-memory checkpoints (full replays after restart)” — outdated. Since ADR-0142, pebble/turso/etc. deployments that leave the store nil already fall through to system’s engine-backed durable default.

Recommendation Stop setting CheckpointStore for sqlite-file deployments; pass the consumer override through or nil, and let system ride the engine. Keep the aux DB solely for the DLQ store; delete applyCheckpointSchema, the eventstore import, and the checkpoint half of buildAuxStores (~60 lines and one sqlite connection gone). Fix the stale doc claims in the same change.
Resolved at cqrs/v0.7.0 Partially Used · Medium impact

Hand-rolled in-flight drain bypasses the Drainer seam — and skips close on drain timeout

cqrs/commands.go:117-180 (inFlightTracker) · cqrs/eventservice.go:690-713 (Shutdown: manual drain, early return)

What the library offers: sys.RegisterDrainer(d) + System.GracefulClose drains all registered Drainer s then closes — and crucially, “if the context expires during draining, Close is still attempted” (System.GracefulClose godoc; seam shipped 2026-08-08, before the wrapper’s v0.5.0 rewrite).

What the project does instead: the wrapper drains its in-flight tracker manually before calling GracefulClose — and on drain timeout returns without ever closing the system, leaking engine handles. The tracker is a perfect Drainer already (Drain(ctx) error); it just isn’t registered.

Recommendation Register the tracker at construction, delete the manual sequencing, and let GracefulClose own the order — smaller surface plus the guaranteed close attempt. 
// In buildSystem, after system.New:
sys.RegisterDrainer(inFile)

// Shutdown collapses to:
func (es *EventService) Shutdown(ctx context.Context) error {
    // ...idempotency guard unchanged...
    return es.sys.GracefulClose(ctx) // drains tracker, closes even if ctx expires
}
Resolved at cqrs/v0.7.0 Missed Opportunity · Medium impact

System health, SCREAM safety, and diagnostics surface unused while go-appkit ships a health module

cqrs/eventservice.go:637-678 (only ReadyCheck / LagPerProjection / staleness exposed) · not used anywhere: sys.HealthCheck, HealthCheckDetailed, VerifyProjections, ScreamReport, Explain, ProjectionExplain, ProjectionPlan, Snapshot (Topology), ShutdownOrder, metaengine Doctor

What the library offers: HealthCheck (K8s-probe-shaped aggregate: engines ping + failed-worker detection), HealthCheckDetailed (per-engine EngineHealth for dashboards), ScreamReport (config-safety findings), VerifyProjections, and rich introspection (Explain, ProjectionPlan, Topology).

Why it matters here specifically: a YAML deployment that forgets a RoleProjections instance silently gets a memory projection store (system constructor.go:173-186 fallback) — persistent event log, volatile read models. SCREAM flags exactly this class of mistake, and the wrapper never surfaces the report. go-appkit’s own health module (go-health bridge) is the natural consumer of EngineHealth; today the two never meet.

Recommendation Add thin accessors (HealthCheck, EngineHealth, ScreamReport) to EventService, document wiring them into appkithealth.NewProbe checks, and log the SCREAM report at construction when it has errors. A full health-module adapter is a natural follow-up module train.
Missed Opportunity · Low-medium impact Resolved at cqrs/v0.7.0 (Deployment shapes README section)

Operator capabilities work via passthrough but nobody documented them

cqrs/README.md:45-62 (Configuration table) · system LoadConfig godoc (full YAML shape)

Reachable today through ConfigPath/Deployment yet absent from every go-appkit doc: multi-bus fan-out (buses + publish, PublisherFor), layout-priority objectives (priority, ADR-0124), operator-declared materialized views (materialized_views, ADR-0135), durability tiers per instance, mixed projection engine pools (engines: [sqlite, pebble]), read-through cache tiers, and SCREAM plan-drift pinning (manifest_path + acknowledge_warnings). A “supported deployment shapes” README section is a cheap, high-leverage doc win — these are precisely the knobs the operator-story exists for.

Not Applicable · judged, not missed

Deliberately out of scope — correctly so

anti-recommendations held: no security/DI/cron in core

Several system/metaengine capabilities are rightly absent from a lifecycle wrapper: NewCachedEventStore / CacheConfig tiers (niche, hot-stream optimization), TieredStore/SwapEngine/ PromoteEngine live-migration machinery (store-level concerns behind System() if ever needed), graph/vector ADTs (no consumer demand), and the adapter types (CommandAdapter, QueryAdapter, EventAdapter) which system already wires internally. Counting these as gaps would be noise; the audit scores them N/A.
