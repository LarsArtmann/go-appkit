00Summary

None of the three libraries is imported by any go-appkit module. That is not neglect — it is the family’s documented opt-in posture, and it has held consistent across four independent records: the 2026-09-16 ecosystem deep-dive (“None of these are underused — they are intentionally indirect”), the battery gap-analysis (which plans go-etag’s promotion via battery B4 and an idempotency store via battery D7), the archived 08-53 utilization audit (“on consumer demand only”), and the module CHANGELOGs. Graph hygiene is clean: every in-graph version equals the newest git tag, the integration module’s exclude block cleanly fences the pre-extraction go-etag root versions, and no replace hacks exist anywhere. What the audit did surface: two TODO-queue sketches — battery D7 (a 165-line idempotency-store port) and the F2 timing-header half (a 116-line CV port + an upstream-ask draft) — were written before their problem space was solved in-family by go-idempotency v0.3.x and httputil/server_timing v1.0.x respectively. Both deserve an adopt-vs-port decision before anyone writes redundant code.

The bottom line Verdict: we do not use them, deliberately — and the posture around not using them is exemplary. Zero direct imports, zero hand-rolled duplicates, zero version debt, every non-use carries a recorded rationale and a demand-gated adoption path. Two planning-doc staleness findings are the only actionable output, both annotation-sized.

01go-etag — intentionally indirect, promotion already planned

Usage evidence. Zero imports in any of the 12 modules. The library appears as // indirect in eight go.mods (entitytag + server, both v0.6.1) for exactly one reason: github.com/larsartmann/httputil requires it — go mod why resolves the chain appkit → httputil → go-etag/server. httputil’s use is a translation table, not ETag emission: errors.go:86-103 registers go-etag’s error codes as human-readable templates and RegisterErrorClassifications() (errors.go:476) folds them into the shared error registry. No appkit code path ever generates or evaluates an ETag; the default middleware stack (middleware.go:14-30: Recovery → RequestID → Logging → [Timeout] → SecurityHeaders) contains no conditional-GET middleware.

Posture verdict: exemplary. Four records agree: the ecosystem deep-dive marks it “intentionally indirect” with a named reach item (an appkit conditional-GET story, “relevant only once a consumer asks for HTTP caching semantics”); the 08-53 audit closed the errorpages conditional-GET idea as “won’t implement — on consumer demand only”; and the battery spec routes adoption through battery B4 Conditional GET in the planned W3 httpx module — explicitly “promotes the unused go-etag indirect dep” (TODO_LIST W3, still accurate). Version currency is perfect: v0.6.1 is the newest tag and sits in every go.mod. The integration module’s exclude block fences the pre-extraction root versions (v0.1.1, v0.3.1, v0.4.0, v0.5.0) so MVS can only resolve the split entitytag/server modules — the documented extraction-safe posture.

02httputil/server_timing — untouched, and now it overtakes a planned port

Usage evidence. Zero imports. The module surfaces only in go.sum (v1.0.2) because Go’s go.mod cannot mark a dependency test-only: httputil’s root module requires server_timing for its own tests, so it rides in every consumer’s module graph (go mod why: appkit → httputil → httputil.test → server_timing). Nothing links it into appkit binaries — unimported packages are never compiled in.

Capability surface (the library is strong). A complete W3C Server-Timing implementation in a stdlib-only module: ServerTimingMiddleware(); nil-safe context helpers (MeasureServerTiming, RecordServerTiming, ServerTimingFromContext — no-ops without the middleware, so handlers need no branching); WrapServerTiming(w, r) for framework-owned chains, which is precisely appkit’s situation; auto-recorded total at first write; Hijack/Flush/Push/Unwrap-preserving writer; metric-name sanitization. The prior deep-dive’s httputil scorecard already recorded “ServerTiming untouched” as a deliberate gap in appkit’s usage of httputil’s broader surface.

The finding. Battery F2 (“Request-ID log correlation + timing header”, ENDORSED at TODO P3) plans to port CV’s 116-line timing.go for an X-Response-Time header, and upstream-ask Draft 3 (2026-09-16) sketches exactly that port. Both predate server_timing v1.0.x. The battery spec itself was written 2026-09-04; the module exists in-family now, is zero-dependency, and covers the “expose request timing to clients” goal with a strictly richer contract (DevTools-readable named metrics, not one opaque duration). X-Response-Time and Server-Timing are different headers with different consumers, so the CV port is not strictly dead — but the default answer for the timing-header half should be wire the sibling, and the plan does not say that today.

03go-idempotency — documented opt-in, and the planned port now overlaps the SDK

Usage evidence. Zero imports in go-appkit. The library (v0.3.1) is indirect in cqrs and integration because go-cqrs-lite/middleware/v4 is built on it: that module ships NewIdempotency[M], CommandIdempotency, EventIdempotency, and QueryIdempotency (middleware/idempotency.go). appkit/cqrs reaches it only as a consumer option and documents the posture in two places: commands.go:18-22 (“Retry, idempotency, and circuit breaking are deliberately NOT defaults — they change command semantics and belong to the consumer (append them via EventConfig.CommandMiddleware)”) and the README’s middleware section (README:617-620), which says the same.

Capability surface (the SDK is mature). A focused at-most-once SDK: the three-method Store interface with the atomicity contract resting on a single CheckAndRecord (the README explicitly warns off the racy Seen-then-Record pattern); deliberately no production backends in-module (Redis/SQL shown as consumer-side adapters); MemoryStore deprecated for production; a contract/ test suite for verifying custom Store implementations; and a middleware/ package with a generic NewCommand wrapper plus an HTTP idempotency-key middleware. The cqrs module’s TODO entry already lists “idempotency/sqlstore” as a candidate EventConfig opt-in, demand-gated.

The finding. Battery D7 (W4) plans a NEW 165-line idempotency store ported from CV’s eventstore, “closes a whole race class”. That description is now also true of go-idempotency v0.3.x — which additionally carries a contract test suite and both command and HTTP middleware wrappers. The battery sketch (2026-09-04) predates the SDK’s current shape. The adopt-vs-port decision should be made explicitly before the port is written; the likely answer is to wire the SDK (implement one Store backend) and keep battery D7’s budget for that backend instead of a parallel store implementation.

04Findings

Battery D7 (165-line idempotency store port) overlaps the go-idempotency SDK
