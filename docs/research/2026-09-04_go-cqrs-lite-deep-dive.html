00Summary

go-appkit/cqrs wraps go-cqrs-lite's SQLite stack and projection host into a lifecycle-managed EventService. At audit start the module did not compile: go-cqrs-lite projectionhost/v4.4.0 replaced its internal flightrecorder/v4 type with go-flightrecorder in WithFlightRecorder, and the wrapper still passed the old type. That migration was executed during this audit, along with the test-hardening and documentation it surfaced. Version currency is otherwise perfect — every pinned module sits on its latest tag.

The bottom line The wrapper's low tooling score (3/27 modules detected by cqrs-lint scorecard) is by design, not underuse: a framework wrapper hands consumers the Bundle() and stays out of the command/query path. The real gaps were the v4.4.0 break (fixed here) and thin documentation of the host-option surface — checkpoint batching and the failure callback were reachable but undocumented (also fixed). Encryption, signing, and idempotency remain genuine future opt-in candidates for EventConfig.

01What the wrapper uses today

The wrapper's job: own lifecycle, expose the stack, and integrate projection health with appkit's service model. It does this with a deliberately small direct-import set (cqrs/eventservice.go:16-21).

+
SQLite stack + projection host, lifecycle-managed sqlite.New + projectionhost.New wrapped with construction-failure cleanup (eventservice.go:101-163) and idempotent Shutdown (eventservice.go:354-367).
+
Dead-letter queue with admin surface SQLite-default DLQ provisioning (eventservice.go:165-199), replay and projection reset accessors, admin interface documented for dashboards.
+
Read-your-writes staleness guards CheckStaleness / CheckProjectionStaleness (eventservice.go:334-344) — the v4-honest answer to async projections, wired for appkit.ServiceConfig.ReadyCheck.
+
Backend-agnostic metrics + OTel adapter Metrics projectionhost.MetricsRecorder with NewOTelProjectionMetrics (otelmetrics.go) — interface-only OTel deps, cardinality-tested.
+
Flight recorder on terminal failures WorkerFailed captures with configurable trigger (eventservice.go:47-66) — migrated to go-flightrecorder in this audit.
+
Companion-tooling cookbook scenario/v4 DSL, testutil/v4 helpers, and cqrs-lint usage documented in the README — dev-only deps kept out of the module's own go.mod, correctly.

02Findings

Ordered by impact. The first two were fixed during this audit.

Blocking · FIXED 2026-09-04

Module did not compile against projectionhost v4.4.0 — flight recorder type changed upstream

cqrs/eventservice.go:212 (pre-fix) · go-cqrs-lite projectionhost/options.go:163

go-cqrs-lite unified its flight-recorder story: projectionhost.WithFlightRecorder now takes *go-flightrecorder.Recorder and a flightrecorder.TriggerFunc instead of the internal flightrecorder/v4.Recorder. The wrapper's EventConfig.FlightRecorder still held the old type, so go build ./... failed — cqrs-lint scorecard silently reported 0% adoption because package loading was poisoned (the exact README gotcha). Fix executed: field migrated to *fr.Recorder, flightrecorder/v4 dropped from go.mod, go-flightrecorder v0.2.0 promoted to direct. 

// Before (broken against v4.4.0)
import "github.com/larsartmann/go-cqrs-lite/flightrecorder/v4"
FlightRecorder *flightrecorder.Recorder

// After — the same type appkit/flightrecorder middleware uses
import fr "github.com/larsartmann/go-flightrecorder"
FlightRecorder        *fr.Recorder
FlightRecorderTrigger fr.TriggerFunc // nil = OnAlways
Side effect: one recorder can now serve both layers HTTP-level captures (appkit flightrecorder middleware) and projection-level captures share ONE fr.Recorder instance. Go still allows only one active recorder per process — start it once at startup.
New capability adopted · DONE

Upstream trigger customization was unreachable — now surfaced as FlightRecorderTrigger

cqrs/eventservice.go:201-220 (hostOptions) · go-cqrs-lite projectionhost/worker.go:126-149

The wrapper passed nil for the trigger, and because derived wiring wins over consumer HostOptions, users could not install their own capture gate. EventConfig.FlightRecorderTrigger fr.TriggerFunc now passes through; upstream evaluates it synchronously with TriggerContext{Kind: "projection", Type: <name>, Err: <terminal error>}. Covered by a new test asserting the context fields (flightrecorder_test.go).

Latent test race exposed · FIXED

v4.4.0 snapshots synchronously — the shared test buffer raced

cqrs/flightrecorder_test.go:33-100 · go-cqrs-lite projectionhost/worker.go:149 (recorder.Snapshot(ctx))

The old internal recorder made the poll-then-read pattern in tests survive -race by timing luck. v4.4.0 calls Snapshot on the worker goroutine, and the race detector fired immediately on the new trigger test. Root-cause fix: a mutex-guarded syncBuffer writer shared by the recorder and the test's length polls — applied to both flight-recorder tests, suite green at -race.

Documentation gap · FIXED

Powerful host options were reachable but undocumented: checkpoint batching and the failure callback

go-cqrs-lite projectionhost/options.go:172 (WithCheckpointEvery), options.go:145 (WithOnFailed) · now in cqrs/README.md config table

WithCheckpointEvery(n) batches live-phase checkpoint saves (added upstream 2026-08-16) — fewer fsync-per-event round-trips at the cost of reprocessing at most n−1 events, a contract projections must already satisfy. WithOnFailed(fn) delivers a synchronous failure callback. Both flow through the wrapper's HostOptions passthrough but appeared nowhere in appkit docs; the README config table now names them. 

eventSvc, _ := cqrs.NewEventService(cqrs.EventConfig{
    SQLitePath: "events.db",
    HostOptions: []projectionhost.HostOption{
        projectionhost.WithCheckpointEvery(100), // batch live-phase saves
        projectionhost.WithOnFailed(func(name, lastErr string) {
            alerting.Page(name, lastErr)
        }),
    },
})
Context · Not a defect

The 24 "missing" scorecard modules: false negatives, routed

cqrs-lint scorecard 4.8.1 on go-appkit/cqrs · go-cqrs-lite stack/bundle.go:38-100

Three groups. (a) Reachable at runtime via Bundle() without a direct import: SnapshotStore, ReadModels (kv), Query journals, codecs, BackwardsSource — the wrapper exposes the whole Bundle. (b) Companion packages by design: scenario, testutil, prometheus (OTel→Prometheus bridge), catalog, otel/v4 — README routes them; appkit's Prometheus readers already go through appkitotel. (c) Genuine future opt-in candidates for EventConfig: event encryption (encryption/v4), event signing (signing/v4), idempotency stores, and scheduling — all security/reliability features a consumer cannot get through the Bundle alone. Routed to the ROADMAP list, not added now: premature wrapper surface without a consumer demanding it is YAGNI.

03Target state (achieved)

One shared go-flightrecorder, one configuration surface, full option visibility: 

// main.go — one recorder serves HTTP middleware AND projections
rec, _ := fr.New(fr.WithFile("trace.out"))
_ = rec.Start()

svc, _ := appkit.NewService(appkit.ServiceConfig{ /* ... */ })
svc.Mux().Handle("/api", flightrecorder.Middleware(rec, fr.OnError(), handler))

events, _ := cqrs.NewEventService(cqrs.EventConfig{
    SQLitePath:            "events.db",
    Logger:                svc.Logger,
    Metrics:               cqrs.NewOTelProjectionMetrics(meter),
    FlightRecorder:        rec, // shared instance
    FlightRecorderTrigger: func(tc fr.TriggerContext) bool {
        return tc.Err != nil // gate captures as needed
    },
})
svc.Config().ReadyCheck = events.ReadyCheck
Why this is better One runtime trace subsystem instead of two fighting over a process-global slot; terminal projection failures and HTTP error bursts land in the same ring; consumers can gate expensive captures; the module compiles against the version it pins.
