00Summary

go-appkit treats OpenTelemetry as a first-class product surface, not a checkbox: a dedicated module (appkitotel, v0.2.0) with a tested provider lifecycle, an otelhttp middleware bridge, SigNoz-grade exception capture, env-driven zero-code OTLP setup, an importable dashboard, and an integration module that pins the whole composition against published tags. Both pinned SDK versions are the latest available — the version gap is zero, verified against upstream releases from 2026-10-02, sixteen days before this audit. Nothing in the codebase is used against the SDK's documented contracts.

The 78/100 comes from the gaps, and the gaps have a shape: the SDK surface the module chose to build is deep and disciplined, while four adjacent capabilities sit at zero — the logs signal, SDK self-diagnostics wiring, client-side spans, and baggage correlation. Two of the four are already ROADMAP-tracked. One, the logs signal, deserves immediate attention for a reason that is documentation, not code: the README's non-goal says "go.opentelemetry.io/otel/log is still experimental" — and on 2026-10-02, upstream shipped v1.47.0, the first stable release of the Logs API and SDK. The module pins v1.47.0 today. The revisit trigger has half-fired; the module's own documentation no longer describes the world it pins.

The bottom line This is what serious OTel adoption looks like — 25 of 37 applicable capabilities fully leveraged, zero misuse, zero version gap. The highest-leverage next moves are small: (1) truth-fix the stale logs non-goal (minutes), (2) wire otel.SetErrorHandler/otel.SetLogger so exporter failures show up in the app's own grep-able log contract instead of dying on stderr (small), (3) ship the ROADMAP-tracked appkitotel.Transport() client-span helper so distributed traces don't terminate at the service edge.

◆What's already excellent

The current usage baseline. Every item is code-verified in this audit; the scored inventory behind them (45 capabilities) is in the appendix.

+
Provider lifecycle that exceeds the typical wiring Setup builds Tracer+Meter providers with resource, views, and sampler; Shutdown ForceFlushes before each provider Shutdown so batch-queued spans from the final requests actually reach the exporter (otel/setup.go:164-192). Errors are classified into go-error-family Infrastructure (503 semantics), not raw fmt.Errorf (otel/setup.go:144-154).
+
Zero-code, env-driven setup with explicit-wins precedence A bare Setup() is fully deployment-configurable: OTEL_EXPORTER_OTLP_ENDPOINT auto-enables OTLP per signal, and OTEL_SERVICE_NAME / OTEL_RESOURCE_ATTRIBUTES / OTEL_TRACES_SAMPLER pass through natively — achieved by deliberately not forcing a sampler. Explicit code options win per signal, so partial migrations are safe (otel/setup.go:338-360). Pinned by a real OTLP/HTTP round-trip test suite against an in-process protobuf collector stub (otel/otlp_test.go, incl. the metric-interval env pin at :260).
+
Semantic-convention discipline on spans, metrics, and exceptions Spans named by matched ServeMux pattern ("GET /users/{id}") to kill route-cardinality blowups (otel/middleware.go:154-165); histogram boundaries pinned to the semconv-recommended bucket set (otel/views.go:19-21); panics and handled errors become exception events with type/message/stacktrace — exactly what SigNoz's Exceptions view indexes (otel/exceptions.go:37-122).
+
Contracts pinned where they can silently rot The integration module (published-tags charter) pins span-name + http.route propagation through the real OuterMiddlewares chain (integration/otel_pattern_test.go:35) and the events-survive-status-clobber behavior (:139). The metric-name surface is a documented contract with a known exporter _ratio trap (doc/TELEMETRY.md §2).
+
Security-aware middleware options WithPublicEndpoint() turns untrusted incoming traceparent headers into links instead of parents, so internet-facing callers cannot forge trace continuity or skew sampling (otel/middleware.go:54-62). Health endpoints are unconditionally filtered from spans/metrics (:167-174). These are options most projects never learn exist.
+
The whole OTel API used as interfaces, never forced on consumers The cqrs module implements projectionhost.MetricsRecorder on raw OTel instruments (cqrs/otelmetrics.go:52) with a stable cqrs.projection.* name contract; the flight-recorder bridge turns capture events into two documented metrics (otel/frmetrics.go:31-63). No exporter is forced — the metric API is interface-only, no-op without Setup.
+
Honest performance evidence Benchmarks for the middleware and Recovery/RecordError with a dated methodology, a ±25% drift rule, and two re-runs proving B/op and allocs/op unchanged across toolchain bumps (otel/README.md:266-312). The strictly-opt-in no-op path is measured, not asserted.
+
Version currency: perfect otel v1.47.0 and otelhttp v0.72.0 are the latest stable releases (upstream, 2026-10-02); contrib v0.72.0 is the pairing release. Zero version gap on either module (otel/go.mod:11-21).

Architecturally, the library owns its edges cleanly: Setup is the only place the SDK is constructed; Middleware bridges otelhttp behind the repo's own httputil.Middleware type; consumers get a Provider.Shutdown that drops straight into ServiceConfig.ShutdownHooks. The module works on plain net/http with no appkit-core dependency, and the process-global registration is skippable (WithoutGlobalRegistration) for tests and multi-service processes. Core stays OTel-free by design — its /metrics endpoint is a dependency-free Prometheus text path, with the divergence between the two metric surfaces documented as a migration trap rather than discovered in production (doc/TELEMETRY.md §2).

Missed opportunity · High impact

The logs signal: the documented non-goal's own trigger fired on 2026-10-02

otel/README.md:252-254 · otel/go.mod:53 (otel/log v1.47.0 already in the tree, indirect) · not used anywhere

The README's design notes declare OTLP logs out of scope because "go.opentelemetry.io/otel/log is still experimental … revisit when it stabilizes and a consumer asks." That sentence is now factually stale: upstream v1.47.0 (the exact version this repo pins) is the first stable release of the Logs API and SDK — go.opentelemetry.io/otel/log and sdk/log are covered by the stability guarantees (only the OTLP log exporters remain v0.x). The stabilization half of the trigger has fired; only the consumer-demand half holds. Meanwhile the fleet already built the other half of log correlation: TraceHandler stamps trace_id/span_id onto slog records (otel/logging.go:24), which stops at text correlation — the logs signal is what makes those records first-class, queryable, trace-linked objects in SigNoz's logs tab. 

// The build path when the consumer-demand half fires (verified against v1.47.0 docs):
import (
    "go.opentelemetry.io/contrib/bridges/otelslog" // v0.21.0
    "go.opentelemetry.io/otel/exporters/otlp/otlplog/otlploghttp" // v0.23.0
    sdklog "go.opentelemetry.io/otel/sdk/log"
)

exp, _ := otlploghttp.New(ctx)                          // same OTLP endpoint as traces
lp := sdklog.NewLoggerProvider(
    sdklog.WithProcessor(sdklog.NewBatchProcessor(exp)))
// register alongside the tracer/meter providers; flush in Provider.Shutdown
otel.SetLoggerProvider(lp)

// bridge the slog stack the fleet already uses:
logger := otelslog.NewLogger("myapp", otelslog.WithLoggerProvider(lp))
Recommendation Two moves, different urgency. (a) Now: rewrite the README non-goal to state the true current status — "Logs API+SDK stable since v1.47.0 (2026-10-02); OTLP log exporters still v0.x; build on consumer demand" — and record the fired trigger where the module tracks revisit conditions. (b) On demand: a WithOTLPLogs() option mirroring the existing WithOTLP() shape, plus an otelslog wiring recipe. The dependency cost is real but small: sdk/log + otlploghttp (v0.x) + the bridge module.
Missed opportunity · High impact

SDK self-diagnostics are unwired: exporter failures vanish to stderr

not used anywhere (rg "SetErrorHandler|SetLogger\(" --type go is empty) · affected path: otel/setup.go:225-257

The OTel SDK reports its own failures — OTLP export errors, dropped batches, sampler misconfigurations — through two process-global hooks: otel.SetErrorHandler(ErrorHandler) for operational errors and otel.SetLogger(logr.Logger) for SDK internal diagnostics. The module wires neither. The default error handler writes to stderr, which means: the batch span processor's documented LOSSY drop behavior (doc/TELEMETRY.md §3 — "queue-full spans/metrics are dropped silently") is silent by construction even though a one-line hook would make it a first-class log line. This directly violates the fleet's own observability doctrine, where every important event is a grep-able, level-classified line in the charmbracelet/slog contract (doc/TELEMETRY.md §1). 

// Inside Setup, after the providers are built (logr v1.4.4 is already an indirect dep):
otel.SetErrorHandler(otel.ErrorHandlerFunc(func(err error) {
    logger.Error("otel export failed", slog.Any("error", err)) // grep-able contract line
}))
otel.SetLogger(logr.FromSlogHandler(logger.Handler())) // SDK internals flow into slog
Recommendation Add both wirings to Setup (opt-out option for exotic embedders), extend doc/TELEMETRY.md §1 with the new line, and pin it in a test. Impact × ease is the best in this report: a deploy where the collector is down currently produces zero evidence in the app's own logs; after the fix it produces one ERROR line per failed export attempt.
Missed opportunity · Medium-high impact

Client-side spans: distributed traces terminate at the service edge

otel/doc.go:68 (mentions otelhttp.Transport for consumers) · ROADMAP.md:90-91 (tracks appkitotel.Transport()) · no otelhttp.NewTransport / otelhttptrace usage anywhere

The middleware produces exemplary SERVER spans; nothing in the fleet produces CLIENT spans. doc.go tells consumers that "outgoing client requests made with otelhttp.Transport continue this service's trace" — true, but the module neither wraps it in an appkit-shaped helper nor documents the pattern outside a doc-comment aside. For an HTTP service framework whose whole pitch is "telemetry in one wiring point," the outbound leg is where real distributed traces die: a call to a payment gateway or downstream service is invisible in the SigNoz waterfall. Upstream also ships otelhttptrace with WithoutSubSpans(), the recommended mode for high-fanout services (DNS/connect/TLS as events, not spans). 

// Proposed (ROADMAP-tracked): one helper mirroring Middleware's shape
func Transport(opts ...MiddlewareOption) http.RoundTripper {
    return otelhttp.NewTransport(http.DefaultTransport, toOtelOpts(opts)...)
}

// Consumer:
client := &http.Client{Transport: appkitotel.Transport()} // CLIENT span per request
Recommendation Export Transport() (the ROADMAP entry already names it), add an "Outbound calls" README section with the otelhttptrace WithoutSubSpans() note, and extend the example with one downstream call. Small API, completes the trace story end to end.
Partially used · Medium impact

Spec's exporter-selector env vars are ignored: no env off-switch for OTLP

otel/otlp.go:22-26, 96-107 · otel/setup.go:338-360 · upstream alternative: contrib exporters/autoexport (v0.72.0)

The OpenTelemetry specification's exporter-selection variables — OTEL_TRACES_EXPORTER, OTEL_METRICS_EXPORTER, OTEL_LOGS_EXPORTER (values: otlp | none | console | prometheus) and OTEL_EXPORTER_OTLP_PROTOCOL — are not consulted. The env path keys strictly off endpoint variables: set OTEL_EXPORTER_OTLP_ENDPOINT and OTLP turns on, with no environment-based off-switch (an operator setting OTEL_TRACES_EXPORTER=none per spec gets traces exported anyway). HTTP-only is a deliberate, defensible posture (gRPC weight avoided) — but the off-switch is a compliance gap, not a design choice. The contrib autoexport package implements exactly this selection layer if full spec coverage is ever wanted.

Recommendation Minimal move: honor OTEL_TRACES_EXPORTER=none / OTEL_METRICS_EXPORTER=none as per-signal vetoes in applyOTLPWiring (a three-line change with a pin test), and state the HTTP-only protocol divergence in the README's production-exporter section. Full autoexport adoption is available if selector breadth (console/prometheus) is ever demanded.
Partially used · Medium impact

Resource detection stops at FromEnv+SDK+Host: no process/runtime attributes

otel/setup.go:376-382 — WithFromEnv(), WithTelemetrySDK(), WithHost(), code attributes win on conflict

The resource merge is correct (code-configured identity beats env, env beats nothing), but the built-in detector set omits resource.WithProcess(), which contributes process.pid, process.executable.name, process.runtime.name, and process.runtime.version (verified against sdk/resource in v1.47.0). Backends surface these in service views; SigNoz's service pages show runtime name/version when present. Container/K8s detectors live in contrib if pod identity ever matters. 

res, err := resource.New(ctx,
    resource.WithFromEnv(),
    resource.WithTelemetrySDK(),
    resource.WithHost(),
    resource.WithProcess(),          // + process.* incl. process.runtime.version
    resource.WithAttributes(attrs...),
)
Recommendation One line in buildResource (plus a test assertion on the merged resource). Note the upstream caveat: WithProcess() includes process.command_args, which can carry sensitive flags — prefer the targeted WithProcessRuntime* options if the full set is too broad.
Partially used · Low-medium impact

semconv pinned at v1.26.0 while the SDK ships v1.43.0 — correct today, plan the rename

otel/setup.go:17 · otel/attributes.go:6 · otel/exceptions.go:13 — all semconv/v1.26.0

The repo emits deployment.environment (via semconv.DeploymentEnvironment), deprecated since semconv v1.27.0 in favor of deployment.environment.name (stabilized v1.40.0 with enum values); the SDK in this very go.mod ships packages up to v1.43.0. The nuance that makes this "partially used" rather than "misused": SigNoz — the module's stated primary backend — still reads the old key by default, with the new key behind a disabled-by-default feature flag (signoz#6921, closed 2026-10-09). The v1.26.0 pin is currently SigNoz-optimal. All other attributes this repo emits (service.name/version/instance.id, exception.*, http.*) are unchanged between the two versions.

Recommendation No code change now. Record the migration trigger: "move to semconv/v1.43.0 + deployment.environment.name when SigNoz flips the semconv-families resolver to default-on" — and note that otelhttp v0.72.0's own metric attributes already follow current semconv regardless of which helper package the repo imports.
Missed opportunity · Low-medium impact

Baggage propagates but nothing speaks it: no correlation-ID helpers

otel/attributes.go:34-37 (Baggage in the propagator) · ROADMAP.md:90 (tracks helpers) · rg "baggage\." --type go is empty

The W3C composite propagator carries baggage on every hop, but no code in the repo ever reads or writes a baggage item. The planned helpers (the ROADMAP's cqrs-parity WithCorrelationID shape) would give multi-service deployments a standard, propagation-native correlation ID that shows up in span attributes automatically — without inventing a custom header protocol. 

// Proposed shape (ROADMAP): set on ingress, read anywhere in the request scope
ctx = appkitotel.WithCorrelationID(ctx, req)   // baggage.SetMember
id := appkitotel.CorrelationID(ctx)            // baggage.Member("").Value()
Recommendation Keep it ROADMAP-gated (no consumer asks yet), but note it in the README's propagation row so consumers know baggage is carried and available.
Partially used · Low impact

Exemplars and cardinality limits: unconfigured, undocumented, mostly fine

otel/frmetrics.go:60-61 · cqrs/otelmetrics.go:108 (both record with context.Background()) · no WithCardinalityLimit anywhere

The SDK attaches exemplars to histogram/counter data points from the active span in the recording context — which means the middleware's HTTP metrics can carry exemplars linking dashboard data points to trace IDs, but the fr-bridge and cqrs recorders, which deliberately use context.Background(), structurally never will. Cardinality is already handled the right way (route patterns, not raw paths), and v1.47.0's default per-instrument limit of 2000 (stable since v1.44.0) backstops any regression. Both topics simply deserve a decided, documented posture rather than silence.

Recommendation Two sentences in the README ("exemplars: available on middleware metrics when spans are sampled; bridge/cqrs metrics opt out by design") and optionally a WithCardinalityLimit view for belt-and-suspenders. No behavior change required.
