00Summary

No — not superbly. The honest picture: one library is used minimally on a dead major version, and two are not used at all. go-appkit's cqrs module pins go-cqrs-lite v3.7.x (tagged 2026-07-07) and wraps exactly 4 of its ~35 module families in a 120-line lifecycle wrapper. Four days after that pin, go-cqrs-lite shipped v4.0.0 (2026-07-11); the entire v4 line — bundle health checks, topological shutdown, SQLite DLQ, lag metrics, the system composition root, the metaengine — is invisible to appkit. cqrs-htmx was planned to be appkit's "first real consumer" (docs/planning/integrations.md:36) but never adopted it: it builds directly on httputil v0.11.0 and go-cqrs-lite v4, duplicating every generic service concern appkit provides, on the same upstream primitives. templ-components has zero relationship with appkit in either direction — yet its errorpage module speaks go-error-family's exact five-family taxonomy and is a ready-made, currently-missed bridge.

The bottom line The single highest-leverage move is migrating the cqrs and docs modules to go-cqrs-lite v4 before v5 unification lands (ADR-0123), and wiring the wrapper properly while doing it (logger, flight recorder, health, DLQ). Second: make a written decision on the cqrs-htmx relationship — the window for appkit to become its foundation is closing as cqrs-htmx's v5 roadmap shrinks it toward upstreams.

01go-cqrs-lite — 28/100

A ~86-module CQRS/event-sourcing monorepo: dispatch, decider, projection hosting, 10+ storage engines, durable timers, event signing/encryption, schema evolution, full OTel/Prometheus observability, BDD scenario DSL, codegen and a 203-rule linter. appkit consumes 4 module families of it, all on the terminal v3 tags.

02go-cqrs-lite — current usage

Two opt-in sub-modules import it. The cqrs module is a single 120-line file (cqrs/eventservice.go) owning a lifecycle wrapper: sqlite.New → projectionhost.New → expose Bundle(), Host(), DB(), StartProjections(), Shutdown(). The docs module (docs-mod/docs.go, 41 lines) wraps catalog.Builder + docserver route mounting for AsyncAPI/OpenAPI/D2.

+
Lifecycle integration is genuinely useful Graceful drain ordering (host.Stop() then bundle.GracefulClose) wired for appkit.Service consumers; idempotent Shutdown via mutex guard (cqrs/eventservice.go:105-120).
+
Error-family classification used correctly NewRejection / WrapInfrastructuref for constructor errors (cqrs/eventservice.go:44-66), matching the project's conventions.
+
StackOptions pass-through keeps the preset open EventConfig.StackOptions forwards sqlite.Option variadics, so WAL/PRAGMA/DSN topology is not hidden (cqrs/eventservice.go:26).
+
Docs module mounts the full docserver surface /docs/openapi, /docs/asyncapi, /docs/diagram, /docs/catalog.json via RegisterDocs (docs-mod/docs.go:34-40).

03go-cqrs-lite — findings

Missed Opportunity · Critical

Pinned to v3.7.x — the entire v4 line (and v5 direction) is invisible

cqrs/go.mod (projectionhost/v3 v3.7.1, stack/sqlite/v3 v3.7.1, stack/v3 v3.7.4) · docs-mod/go.mod (catalog/v3)

v3.7.1 was tagged 2026-07-07; v4.0.0 shipped 2026-07-11 — four days later. Since then: stack v4.3.0, catalog v4.2.1, command/event v4.6.0, metaengine v4.10.0. The v4 line adds Bundle.HealthCheck, WithShutdownDependency (topological close ordering), durability tiers, machine-checkable capability flags, projectionhost lag metrics (LagPerProjection/Status()), SQLite DLQ + admin, WithPurgeDeadLetters, and CBOR codec defaults. v5 unification (ADR-0123) is already in progress; v3 is a dead end that will never receive these.

Recommendation Migrate both modules to v4 before building anything further on v3. The migration guide is mechanical (module paths /v3→/v4, alias removals, codec default flip). Time it before v5 to avoid doing it twice.
Risk · High impact

v3 stack/sqlite lacks the WAL single-writer pool cap — SQLITE_BUSY under concurrent writers

cqrs/eventservice.go:47 (sqlite.New) · evidence: go-cqrs-lite CHANGELOG 2026-08-15 (benchkit entry)

stack/sqlite v4.3.0 added SetMaxOpenConns(1) to cap concurrent WAL writers. go-cqrs-lite's own CHANGELOG documents that pinning a pre-v4.3.0 stack/sqlite caused "instant SQLITE_BUSY (517)" under concurrent writes in their own benchmark suite. appkit's v3.7.1 pin has exactly that hole: any appkit service with concurrent command dispatch can hit SQLITE_BUSY with no retry shield.

Recommendation The v4 migration (finding #1) is the real fix. If v3 must stay short-term, document the risk and route writes through a single dispatcher.
Partially Used · High impact

projectionhost wired bare: no logger, no metrics, no flight recorder, no DLQ

cqrs/eventservice.go:57 (New without options)

projectionhost.New(bundle.SeekableJournal, bundle.CheckpointStore) is called with zero options. The library offers WithLogger, WithMetrics, WithDeadLetterStore, WithFlightRecorder, WithBackoff, WithBatchSize — none wired. The irony is sharp: appkit ships its own flightrecorder module and its own logger, and connects neither to the component that would benefit most. Poison events vanish silently (no DLQ), and projection crashes restart invisibly.

Recommendation Thread appkit's logger through EventConfig, and add a flight recorder option: 
// EventConfig gains:
Logger         *slog.Logger
FlightRecorder *fr.Recorder   // appkit's own module!
DLQ            event.DeadLetterStore

opts := []projectionhost.HostOption{}
if cfg.Logger != nil {
    opts = append(opts, projectionhost.WithLogger(cfg.Logger))
}
if cfg.FlightRecorder != nil {
    opts = append(opts, projectionhost.WithFlightRecorder(cfg.FlightRecorder))
}
host, err := projectionhost.New(journal, checkpoints, opts...)
Anti-Pattern · Low impact

fmt.Errorf in DB() violates the project's own error rule

cqrs/eventservice.go:91

AGENTS.md: "Errors use go-error-family constructors instead of fmt.Errorf." The very next file breaks it: DB() returns fmt.Errorf("cqrs: database is not *sql.DB ..."). It is also the only error in the module that will not classify for HTTPStatus()/LogError().

Fix errorfamily.NewRejection("cqrs.db_not_sql", "database is not *sql.DB (got %T)", ...) — or Corruption family if it indicates store damage.
Partially Used · Medium impact

Projection health is invisible to appkit's readiness probe

cqrs/eventservice.go:99-101 · appkit health.go

appkit's core value is the ready probe + graceful drain, yet EventService exposes no readiness signal. projectionhost v4 has Status(), LagPerProjection(), and stack v4 has HealthCheck(ctx). cqrs-htmx built exactly this bridge (ProjectionReadinessCheck: 503 while projections are idle/running/backoff/draining/failed). appkit's cqrs module should offer the same so /health/ready tells the truth before traffic arrives.

Partially Used · Low impact

host.Stop() error swallowed during shutdown

cqrs/eventservice.go:117

_ = es.host.Stop() discards the drain error while GracefulClose's error is returned. A projection that fails to drain is silently lost — the exact scenario graceful shutdown exists to surface. v4's WithShutdownTimeout makes the error meaningful.

Missed Opportunity · Medium impact

Observability modules (otel, prometheus) never imported

not used anywhere in go-appkit

go-cqrs-lite ships a complete observability stack: otel.Setup() with canonical CQRS span attributes and correlation-ID baggage, prometheus.Setup() with an OTel→Prom bridge and /metrics handler, and projectionhost WithMetrics hooks. appkit positions itself as the service framework yet offers no metrics path for the event store it manages. A single opt-in cqrs.WithMetrics()-style accessor would compose them.

Nice to have · Strategic

Hardwired to SQLite while 8 stack presets exist

cqrs/eventservice.go:47

stack presets exist for postgres, mysql, pebble, bbolt, duckdb, turso, memory — and v4's system package makes engine choice an operator-level YAML/env decision. appkit accepting only SQLitePath forces every consumer onto embedded storage. Not urgent, but the v4 migration is the moment to decide whether EventService stays sqlite-shaped or becomes stack-generic.

Nice to have · Developer experience

testutil and scenario (BDD) invisible to appkit consumers

not used anywhere in go-appkit

go-cqrs-lite's scenario DSL (GivenDecider/GivenProjection), testutil helpers, and cqrs-lint (203 rules) are free quality leverage for any appkit+cqrs consumer. Even documenting them in the cqrs module README would capture most of the value at zero dependency cost.

05cqrs-htmx — 0/100 integration

cqrs-htmx v4.8.0 is the flagship application framework of the ecosystem: one-line command/query→HTTP wiring, HTMX response builders, embedded admin/dashboard/login UIs, an event-sourced usermgmt service, offline sync, and its own SSE stack. The relationship question is inverted for this one: appkit was never going to import it — cqrs-htmx was supposed to import appkit. It never did.

Strategic · High impact

The "first real consumer" plan is dead — and nobody wrote the obituary

docs/planning/integrations.md:36 vs cqrs-htmx/go.mod (httputil v0.11.0, go-cqrs-lite v4, go-sse v0.5.0 — no appkit)

appkit's planning docs state cqrs-htmx would be appkit's first real consumer. Verified today: rg -i 'appkit' across the entire cqrs-htmx repo returns zero matches. Its setup.Bundle.Run() owns a listener via httputil.NewServer directly. Meanwhile every generic concern appkit exists to provide is duplicated there on the same upstreams:

Concern appkit cqrs-htmx's own version
Panic recovery httputil.Recovery own RecoveryMiddleware (errorfamily+requestID-aware)
Request/correlation ID httputil.RequestID own ContextEnrichmentMiddleware
Request logging httputil.Logging + charmbracelet own RequestLoggingSlog (+family/error_code attrs)
Security headers httputil.SecurityHeaders RecommendedSecurityMiddleware (same httputil)
Health/ready /health/live + /health/ready + drain probe ReadinessHandler + ProjectionReadinessCheck + healthz/readyz
SSE hub realtime.Hub (heartbeat/CORS/replay/filter) Broadcaster over go-sse + JournalSSEStore + ACK
Server lifecycle Service.Run/Shutdown + drain setup.Run via httputil.Server
Auto-docs docs module (catalog docserver) catalog/v4 docserver (same module appkit wraps!)

cqrs-htmx's v5 roadmap retires its 39 httputil re-exports and shrinks toward upstreams — the moment where a shared service foundation pays off. If appkit wants that role, its unique, non-duplicated value is narrow and specific: the LB drain probe, listener-owned Addr() net.Addr, charmbracelet pretty logging, and the flightrecorder middleware.

Recommendation — decide, then document Either (a) make setup.Run's server layer pluggable and prototype appkit.Service inside cqrs-htmx's setup module, or (b) formally retire the "cqrs-htmx will consume appkit" line from docs/planning. An unwritten decision is how ecosystems grow two of everything.
Missed Opportunity · Medium impact

SSE: same upstream, zero interop, complementary gaps

realtime/handler.go (CORS, replay, filtering) vs cqrs-htmx sse_broadcaster.go / event_store_sse.go (journal-durable replay, ACK, no CORS)

appkit's realtime module and cqrs-htmx's SSE stack both build on go-sse v0.5.0. appkit has CORS handling, heartbeat config, and event filtering; cqrs-htmx has journal-durable replay (JournalSSEStore over event.Journal) and a command-ACK protocol — and no CORS handling. The natural composition (cqrs Journal → SSE EventStore bridge in appkit) exists in neither repo. Building it in appkit/realtime would make realtime the SSE endpoint of record for the whole ecosystem.

06templ-components — 0/100, one cheap win

116 templ + Tailwind v4 components, 106 icons, golden-file and chromedp visual-regression gates, CSP-nonce discipline. Correctly not an appkit dependency: it is a UI layer for applications. But one submodule was practically designed for a service framework like appkit and nobody connected the wires.

Missed Opportunity · High impact · Low effort

errorpage speaks go-error-family natively — appkit's exact error taxonomy, unused

not used anywhere in go-appkit · errorpage/handler.go (standalone module, deps: templ, go-error-family v0.10.0)

templ-components/errorpage is a standalone Go module whose ErrorHandler(err, cfg) http.Handler classifies via go-error-family — the same five families appkit re-exports through HTTPStatus() (Rejection→400, Conflict→409, Transient→503, Corruption→500, Infrastructure→503). It renders styled What/Why/Fix error pages (or JSON) with prebuilt 404/403/409/503 constructors, plain-text fallback if rendering fails, and a documented JSON contract {family, code, message, title, why, fix, context} that templ-components' own htmx.GlobalErrorHandling parses client-side into family-mapped toasts. appkit consumers currently get naked status codes.

Recommendation Add an opt-in sub-module (same pattern as realtime/cqrs, keeps jsonv2 out of core): 
// go-appkit/errorpages: optional pretty errors
import errorpage "github.com/larsartmann/templ-components/errorpage"

// registers a not-found handler + wraps 5xx via errorfamily
errorpages.Mount(svc.Mux, errorpages.Config{ServiceName: "myapp"})
// consumers using templ-components get toasts for free:
// htmx.GlobalErrorHandling parses the same JSON contract

Constraint to respect: errorpage requires GOEXPERIMENT=jsonv2 (encoding/json/v2) — already required by appkit's realtime module, so the pattern is established. HTML mode additionally needs the host's Tailwind build; JSON mode is framework-neutral.

Upstream finding · courtesy fix

errorpage: 6th family (FamilyOrchestration) missing from FamilyStatusCode map

templ-components/errorpage (status map)

go-error-family's taxonomy now has a sixth family (Orchestration); errorpage styles it but omits it from the status-code map, so it silently falls back to 500. Worth an upstream ticket/PR once verified against go-error-family's intended mapping.

07Ecosystem view — the split brain

The three audits reduce to one structural problem: appkit and cqrs-htmx both assemble service frameworks from the same upstreams, one major version apart on the CQRS engine.

appkit — httputil v0.11 · cqrs-lite v3.7 · go-sse v0.5 → health · SSE · docs · lifecycle
cqrs-htmx — httputil v0.11 · cqrs-lite v4.6 · go-sse v0.5 → health · SSE · docs · lifecycle

Two parallel assemblies, zero imports between them, and a v3/v4 fault line across the only shared domain library. Also noted: appkit's AGENTS.md has drifted — it documents httputil v0.9.1 and go-sse v0.4.0 while go.mod pins v0.11.0 and v0.5.0.
